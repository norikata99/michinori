# 0001. アプリとインフラを1つのリポジトリで管理する

- ステータス：採用
- 日付：2026-11-07

## 背景
みちのりは、Laravelのアプリ（`src/`）、コンテナの定義（`docker/`）、AWSの構成（`infra/`、Terraform）、CI/CD（`.github/workflows/`）から成る。開発者は1人。

これらは一緒に変わることが多い。たとえば、環境変数を1つ追加すると、アプリの設定、Dockerfile、ECSのタスク定義、Terraformの秘密情報の定義をまとめて変更することになる。

## 決定
アプリとインフラを同じリポジトリ（モノレポ）に置く。

- Laravelは `src/` に置く（Laravel自体が `app/` ディレクトリを持つため、ルートに置くと区別しにくい）
- GitHub Actionsのワークフローは、変更されたパスで分ける
  - `app.yml`：`src/`・`docker/` の変更時
  - `infra.yml`：`infra/` の変更時

## 検討した代替案
### アプリとインフラでリポジトリを分ける
- 利点：リポジトリ単位で権限を分けられる。インフラの変更履歴がアプリの変更に埋もれない
- 欠点：1つの変更が2つのPRに分かれ、順番を揃えてマージする必要がある。どのアプリのバージョンがどのインフラの状態で動いているかを追いにくい
- 開発者が1人の今の規模では、欠点の方が大きいと判断した

## 結果
- 1つのPRで、アプリとインフラの変更をまとめてレビュー・マージできる
- パスで分けないと、READMEを直しただけでデプロイや `terraform plan` が走る。ワークフローのトリガーに `paths` を必ず指定する
- リポジトリ単位で権限を分けられない。代わりに、GitHub ActionsがOIDCで引き受けるIAMロールを「アプリのデプロイ用」と「Terraform用」に分けて補う（`docs/design.md` 8章）
- チームが大きくなり、インフラの担当者が分かれる場合は、リポジトリを分けることを再検討する
