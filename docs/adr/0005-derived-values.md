# 0005. 実績工数などの派生値は保存せず、作業ログから集計する

- ステータス：採用
- 日付：2026-11-13

## 背景
このアプリは、予定と実績のズレを見せる。ズレを出すには、次の実績の値が必要になる。

| 値 | 元になるデータ |
|---|---|
| タスクの実績工数 | そのタスクの作業ログの `minutes` の合計 |
| タスクの実績開始日 | そのタスクの作業ログの `worked_on` の最小値 |
| ゴールの実績工数・実績開始日 | 配下のタスクの作業ログから、同じように集計 |
| ゴールの見積もり | 配下のタスクの `estimated_minutes` の合計 |

これらを `tasks` や `goals` に列として持つか、表示のたびに集計するかを決める。

## 決定
- **派生値は保存しない**。表示のたびに作業ログ（とタスク）から集計する
- 集計は SQL の `SUM`・`MIN` で行う
  - ゴールの詳細画面のタスク一覧は、`withSum`・`withMin` でまとめて集計し、タスクごとにクエリを投げない（N+1 を避ける）
- ズレの計算（工数の差、日数の差）は PHP（`App\Support\Progress`）で行う
  - 工数のズレ：実績 − 見積もり（分）
  - 日程のズレ：終わった日 − 予定の終了日（日）。タスクは `completed_at` と `planned_end`、ゴールは `achieved_at` と `planned_end`（締切）。終わっていなければ出さない

## 理由
- **値がずれない**：作業ログは後から直したり消したりする。実績を列に保存すると、ログを直すたびにその列も直す必要がある。直し忘れやバグがあると、画面の値とログの合計が食い違う。集計なら、ログが正しければ表示も必ず正しい
- **この規模なら集計は軽い**：1つのゴールのタスクは数十件、ログは数百件程度の想定。`task_id` に索引があるので、集計の負荷は問題にならない
- **日数の差を PHP で計算する理由**：日付の差を出す関数は、MySQL（`DATEDIFF`）と SQLite（`julianday`）で書き方が違う。テストは SQLite、本番は MySQL で動かしているため、どちらでも同じ結果になる PHP で計算する。`SUM`・`MIN` はどちらの DB でも同じように動く

## 検討した他の案
- **実績を列に保存し、ログの保存・削除時に更新する**：一覧の表示は速くなるが、上の「値がずれる」問題がある。表示が遅くなってから検討する
- **日数の差も SQL で計算する**：DB ごとに書き分けるか、テストを MySQL に揃える必要がある。今は PHP で十分

## 影響
- 一覧で集計を出すときは、`withProgress()`（`withSum` + `withMin`）を使う。使い忘れても値は正しいが、タスクごとにクエリが増える
- データが大きく増えて集計が重くなったら、保存する案（または集計結果のキャッシュ）を検討し直す
- `SUM`・`MIN` の結果は、DB やドライバーによって文字列で返ることがある。`Progress::fromAggregates()` で数値・日付に変換する
- 確認したこと：同じテスト（85件）が SQLite と MySQL 8.4 の両方で通る
