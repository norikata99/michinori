# みちのり（Michinori）設計と決定事項

作成日：2026-11-06（claude.aiでの壁打ちの結果をまとめたもの）

## 0. 名称
- アプリ名：みちのり（Michinori）
- リポジトリ名：`michinori`
- 一言紹介：予定と実績のズレが見える目標管理アプリ（READMEの1行目とリポジトリの説明欄に使う）
- 由来：ゴールまでの道のり。予定の道のりと実際に歩いた道のりを比べる

## 1. 目的と方針
- AWSでのインフラ設計・構築・運用を実践するための個人プロジェクト
- アプリは小さく、インフラを厚く
- 機能を広げるより、各判断の理由と代替案を説明できる状態を優先する
- 期間の目安：約1ヶ月

## 2. スコープ
### 入れる
- 認証（Laravel Breeze、マルチユーザー）
- ゴールとタスクのCRUD
- 予定と実績（作業ログ）の記録
- ズレの集計（工数のズレ、日程のズレ）
- ガント表示（既製ライブラリで表示のみ。余力があれば）
  - ゴールの締切と今日の位置に線を引き、締切を越えるタスクや、予定日を過ぎても終わっていないタスクが見てわかるようにする

### 入れない
- タスクの親子関係、タスク間の依存関係、タグ
- 締切超過の警告（下記4章）

### 遅れた時に削る順番
1. ガント表示
2. 監視の細部
3. アプリ機能

IaCとCI/CDは削らない。

## 3. データモデル
```
users      Laravel標準
goals      id, user_id, title,
           planned_start, planned_end, achieved_at, status
tasks      id, goal_id, title,
           planned_start, planned_end, estimated_minutes,
           status, completed_at
work_logs  id, task_id, worked_on(日付), minutes, note
```

- goals.status：進行中 / 達成 / 中止（試験不合格で立て直すケースのため「中止」を残す）
- tasks.status：未着手 / 作業中 / 完了（`todo` / `doing` / `done`）。完了にすると `completed_at` に完了日が入る（空なら今日。完了以外に戻すと消える）
- 状態の列は文字列 + CHECK 制約 + PHP の enum で持つ（`docs/adr/0004-status-columns.md`）
- goals.achieved_at は記録として持つ。「配下タスクが全部終わった日」とは別の出来事のため自動計算しない

### 保存せず集計で出す値
- タスクの実績工数：work_logs.minutes の合計
- タスクの実績開始日：work_logs.worked_on の最小値
- ゴールの実績工数・実績開始日：配下タスクのログから同様に集計

保存するとログ修正時に値がずれるため、派生値は持たない。

## 4. アプリの見せ場
- 工数のズレ：estimated_minutes と実績工数の差
- 日程のズレ：planned_end と completed_at の差

締切超過の警告（ゴールの締切と、配下タスクの最も遅い planned_end を比べる）は、当初は入れる予定だったがやめた（#11）。予定どうしを比べるため、予定を立てる時点で締切より後のタスクを入れることはまずなく、出番がほとんどない。締切を越える予定は、ガント表示で締切の線と並べて見えるようにする。

## 5. リポジトリ構成
モノレポ（アプリとTerraformを同じリポジトリに置く）。構成は `CLAUDE.md` を参照。

- Laravelは `src/` に置く（Laravel自体に `app/` があるため）
- GitHub Actionsはパスで分ける。分けないとREADME修正だけでデプロイやplanが走る
- 環境は `envs/` で分けられる構造にし、実際に動かすのは1環境のみ（コスト対策）
- tfstate用S3は `bootstrap/` で別管理（鶏と卵の問題を避けるため）

### 公開方針
- **パブリックリポジトリ**とする。誰でもリンク一つでコードと設計判断を見られるようにするため
- 最初からパブリックで始める。「プライベートで作って完成後に公開」は避ける（誤ってコミットした秘密情報が、公開時に履歴ごと出てしまうため）
- 対策：
  - 最初のコミットから `.gitignore` に `.env` と `*.tfvars` を入れる
  - GitHubのシークレットスキャンとプッシュ保護を有効にする
  - OIDCの信頼ポリシーは「このリポジトリ」かつ「mainブランチまたは特定のEnvironment」に限定する（誰でもフォークしてPRを出せるため、条件が緩いと他人のワークフローからAWSを操作される）
  - AWSのアカウントIDは秘密情報ではないが、コードに直接書かず変数や出力から参照する

## 6. ローカル環境（Docker）
以前の環境は使わず作り直す。最初から本番のECSでそのまま動く前提で設計する。

- nginxとphp-fpmの2コンテナ構成。ECSでは同じタスク定義に2コンテナを置き、localhostで通信
- マルチステージビルド
  - 開発用：ソースはbind mount、Xdebugなどの開発ツール入り
  - 本番用：ソースをイメージにコピー、`composer install --no-dev`
- **注意**：本番ではnginxイメージにも `public/`（CSS・JS）をコピーする。忘れるとCSSが当たらない
- DB：ローカルはMySQLコンテナ。本番RDSとメジャーバージョンを揃える
- `.env` はイメージに含めない
- ログは標準出力へ（`LOG_CHANNEL=stderr`）
- ローカルはhttpのlocalhostで十分

## 7. AWS構成
### アカウント
- AWS Organizationsのメンバーアカウントを1つこのアプリ専用にする（コストの切り分けのため）

### DNSと証明書
- 本番ドメイン：`app.noritaka.dev`
- `noritaka.dev` はCloudflare Registrarで取得。Cloudflare Registrarはネームサーバーを変更できないため、ドメイン全体をRoute 53に移すことはできない
- **採用：サブドメインだけRoute 53に委任する**
  1. Route 53に `app.noritaka.dev` のホストゾーンを作成
  2. 割り当てられた4つのネームサーバーを、CloudflareのDNSに `app` のNSレコードとして登録（手作業はこの一回のみ）
  3. `dig +trace app.noritaka.dev` で委任されていることを確認（未検証。必ず確認する）
- ACM証明書はRoute 53でDNS検証し、Terraformで自動化する
- `noritaka.dev` 本体（GitHub Pages）には影響しない

### ネットワーク
- VPCは2AZ（ALBとRDSはどちらも2AZ分のサブネットが必須）
- サブネット：パブリック（ALB）、プライベート（ECS）、DB用（RDS）を各AZに1つずつ
- **外向き通信：NAT Gateway 1つ（プライベートサブネット経由）**
  - 本番構成としてはVPCエンドポイントが望ましいが、今回は構成のシンプルさを優先
  - 将来VPCエンドポイントへ移行できるよう、ECSタスクは最初からプライベートに置く
  - S3のゲートウェイ型エンドポイントは無料なので最初から入れる（ECRのイメージ本体はS3から取得されるため、NAT経由の通信量も減る）
  - networkモジュールに切り替え用変数を用意する（例：`egress_mode = "nat"` / `"vpc_endpoint"`）
  - 弱点：NATを置いたAZが落ちると、もう片方のAZのタスクも外に出られない。認識した上での選択としてADRに残す

### コンピュートとDB
- ECS Fargate、ALB（HTTPSはALB + ACMで終端）
- RDS for MySQL、シングルAZ。最終スナップショットは取らない設定（作り直し前提）
- 秘密情報はSSMパラメータストアかSecrets Managerから注入（どちらにするかは未決定）

### 公開デモ
- `app.noritaka.dev` を常時公開すると誰でもユーザー登録できるため、扱いを決める必要がある（未決定）
- 選択肢の例：デモ用アカウントを用意して新規登録を止める／使わない時は環境を落とす

### コスト
- ALB、RDS、NAT Gateway、パブリックIPv4は置いておくだけで課金される
- 使わない時は `terraform destroy` できる作りにする
- 料金の具体額は変わるため、構築前に料金ページで確認する

## 8. CI/CD
- **タスク定義の管理分担**：初回はTerraformで作成し、以降のイメージ更新はCIが担当。Terraform側はサービスのタスク定義の変更を `ignore_changes` で無視する（両方が更新すると apply のたびに古いイメージへ戻る衝突が起きるため）
- **DBマイグレーション**：デプロイ前に、同じイメージで単発のECSタスク（`run-task`）として実行。コンテナ起動時には流さない（複数タスクが同時に実行して衝突する恐れ）
- **デプロイ方式**：まずローリング更新 + デプロイサーキットブレーカー（失敗時の自動ロールバック）。余力があればECS組み込みのBlue/Green（2025年7月から利用可能、CodeDeploy不要）に切り替えて比較する
- **Terraform**：PRで `plan` を実行して結果をコメント。`apply` はmainへのマージ後、GitHubのEnvironmentの承認を挟んで実行
- **権限**：OIDCで引き受けるIAMロールを「アプリのデプロイ用」と「Terraform用」に分ける。デプロイ用は最小権限
- **イメージ**：タグはgitのコミットSHA。ECRはタグの上書き禁止
- **チェック**：PHPUnit、Pint、`terraform fmt`、イメージの脆弱性スキャン

## 9. 監視
- ヘルスチェック：Laravelの `/up` をALBのヘルスチェック先にし、DB接続も確認する
- アラーム：ALBの5xx、異常なターゲット数、ECSのCPU・メモリ、RDSのCPU・空きストレージ・接続数
- 通知：SNSからメール（Slack・Discordは後から追加可能）
- ログの保存期間：30日程度（標準は無期限で費用が積み上がる）

## 11. ADRに書く候補
- モノレポにした理由
- Fargateを選んだ理由
- 外向き通信をNAT Gateway 1つにした理由と、VPCエンドポイントへの移行手順
- サブドメインをRoute 53に委任した理由（Cloudflare Registrarの制約）
- タスク定義の管理をTerraformとCIで分担した理由
- マイグレーションを単発タスクで実行する理由
- 派生値（実績工数など）を保存しない理由
- パブリックリポジトリでのOIDC信頼ポリシーの絞り方
